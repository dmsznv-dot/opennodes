**Расписание и Telegram.** Раньше триггеры `trigger.cron` и `trigger.telegram` только описывались: сценарий с ними можно было опубликовать, но он никогда не срабатывал. Теперь публикация регистрирует триггер, а запуски создаёт worker (в режиме `embedded` — API). Расписание задаётся пресетом («каждый день в 09:00») или cron-выражением в часовом поясе, переход на летнее и зимнее время учитывается. Запуск, пропущенный, пока ничего не работало, по умолчанию пропускается (`catchUp: "once"` — выполнить один раз). Бот Telegram опрашивается через `getUpdates`, есть фильтр команд; сообщения, отправленные до публикации, не обрабатываются. Каждое срабатывание расписания и каждое сообщение дают ровно один запуск даже при нескольких worker'ах и перезапусках. Неверное расписание или отсутствие подключения бота → публикация отклоняется (422 `ERR_TRIGGER_INVALID`). `GET/PUT /workflows/:id/triggers` показывает следующий и последний запуск и ошибки опроса, ставит триггер на паузу. Проверено: `apps/api/tests/triggers.test.ts`, `packages/execution-runtime/tests/cron.test.ts`, тест гонки двух планировщиков, живой прогон с перезапуском API — расписание «каждую минуту» сработало в 19:19:01 и завершилось SUCCEEDED. С настоящим ботом Telegram не проверялось, только на поддельном сервере Bot API.

**S-14 — частично.** Добавлены `GET /me`, `POST /auth/logout`, `GET /catalog` (какие шаги сервер умеет выполнять), `GET/DELETE /workflows/:id`, `PUT /workflows/:id/active`, `POST /workflows/:id/test-run`, `GET /workspaces/:id/executions` (запуски с шагами), `DELETE` и `GET …/check` для подключений; создание сценария с id от клиента, переименование через `PUT /draft`. Публикация включает сценарий, выключенный сценарий не принимает вебхуки (409). Не сделано: приглашение пользователей и выдача ролей.

**Найдено при проверке в браузере: исходящие запросы по имени хоста не работали вообще.** Защищённый HTTP-клиент «закрепляет» проверенный IP через свой `lookup`, но Node 20+ вызывает его с `all: true` и ждёт список — каждый запрос к `api.telegram.org`, `api.openai.com` и к `localhost:1234` (LM Studio) падал с `Invalid IP address: undefined`. Тесты этого не видели: они ходили на `127.0.0.1`, где DNS не участвует. Исправлено в `packages/shared/src/ssrf/agent-pinning.ts`: отдаётся весь список проверенных адресов (IPv4 и IPv6), регрессионный тест — `packages/shared/tests/pinned-lookup.test.ts`; настоящий запрос к Telegram с поддельным токеном теперь получает ответ `401 Unauthorized`.

**Локальные модели.** Подключение типа `openai-compatible` (`baseUrl`, необязательные `apiKey` и `defaultModel`) позволяет вызывать из шага `ai.openai` любой локальный сервер моделей с OpenAI API: LM Studio, Ollama (`/v1`), llama.cpp `llama-server`, Jan, vLLM. `GET /workspaces/:id/credentials/:credentialId/models` проверяет подключение и показывает загруженные модели. Локальные адреса закрыты SSRF-политикой, пока их не добавят в `SSRF_ALLOWLIST`; ошибка шага подсказывает, что добавить. Проверено на поддельном OpenAI-совместимом сервере; с настоящими LM Studio/Ollama не запускалось. Инструкция — в README, раздел «Local models».

Секрет вебхука теперь хранится зашифрованным (AES-256-GCM, привязан к id сценария) и больше не возвращается в ответе на создание сценария.

## Как проверяли

Docker на машине не установлен, поэтому `docker compose up` не запускался. На момент проверки API не использовал ни Postgres, ни Redis: всё хранилось в памяти процесса (`Map`, `MemorySessionStore`, `InMemoryExecutionJournal`), сценарии выполнялись прямо в API. Поэтому основной путь проверен на живом процессе `node apps/api/dist/index.js` по HTTP — в контейнере API ведёт себя так же.

Путь: health → setup → вход → 401/403 → учётные данные → сценарий → цикл → публикация → запуск → просмотр → вебхук (HMAC, идемпотентность) → **перезапуск процесса** → повторная проверка. Роли VIEWER и доступ чужого пользователя проверены в процессе через `createTestUser` / `grantWorkspaceRole`, так как API для приглашения пользователей нет.

## Что работает

- Повторный `/setup` блокируется (409) — пока процесс жив.
- Вход: неверный пароль → 401, email без учёта регистра; без токена / с плохим токеном → 401; чужое пространство → 403.
- Учётные данные шифруются, в списке только маска (`••••••••-ABC`).
- Публикация отклоняет цикл (`ERR_CYCLIC_DEPENDENCY_DETECTED`, 422) и запуск неопубликованного (400).
- Выражения и типы: `Hi {{ $trigger.name }}` → `Hi Аня`, `0` и `false` сохраняются.
- Секреты во входе маскируются в результатах шагов (`[REDACTED]`).
- Вебхук: неверная подпись → 401, повтор с тем же `x-idempotency-key` дедуплицируется.
- VIEWER: читает, но не может править, публиковать, запускать, создавать учётные данные, отменять (403).

## Что не проверено

- Сам `docker compose up` (нет Docker): сборка образов, healthcheck'и, тома. S-3 и S-4 выведены из кода и локальной сборки.
- Worker с настоящими Postgres и Redis: восстановление после сбоя, задержки, очередь.
- Одновременное редактирование: в API нет ни версий черновика, ни детекта конфликтов — сохраняет последний.
- 429, таймауты и отключённый worker — их негде вызвать, пока коннекторы не подключены (S-2).

## Что чинить и в каком порядке

1. **Хранение в Postgres** для пользователей, сессий, пространств, сценариев, учётных данных и запусков (S-1) + запуск миграций при старте (S-3). Без этого любой перезапуск — потеря данных и захват сервера.
2. **Подключить коннекторы к движку** и падать с понятной ошибкой на неизвестном типе узла вместо pass-through (S-2).
3. **Решить, кто исполняет:** либо API ставит запуски в BullMQ и их берёт worker, либо worker пока убрать из compose (S-3).
4. Закрыть S-5 и S-6, сделать честный `/health/ready` (S-7).
5. Веб-сервер в `apps/web` (S-4) — это и есть следующий этап «настоящее веб-приложение».
