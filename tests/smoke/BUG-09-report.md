Секрет вебхука теперь хранится зашифрованным (AES-256-GCM, привязан к id сценария) и больше не возвращается в ответе на создание сценария.

## Как проверяли

Docker на машине не установлен, поэтому `docker compose up` не запускался. На момент проверки API не использовал ни Postgres, ни Redis: всё хранилось в памяти процесса (`Map`, `MemorySessionStore`, `InMemoryExecutionJournal`), сценарии выполнялись прямо в API. Поэтому основной путь проверен на живом процессе `node apps/api/dist/index.js` по HTTP — в контейнере API ведёт себя так же.

Путь: health → setup → вход → 401/403 → учётные данные → сценарий → цикл → публикация → запуск → просмотр → вебхук (HMAC, идемпотентность) → **перезапуск процесса** → повторная проверка. Роли VIEWER и доступ чужого пользователя проверены в процессе через `createTestUser` / `grantWorkspaceRole`, так как API для приглашения пользователей нет.

## Что работает

- Повторный `/setup` блокируется (409) — пока процесс жив.
- Вход: неверный пароль → 401, email без учёта регистра; без токена / с плохим токеном → 401; чужое пространство → 403.
- Учётные данные шифруются, в списке только маска (`••••••••-ABC`).
- Публикация отклоняет цикл (`ERR_CYCLIC_DEPENDENCY_DETECTED`, 422) и запуск неопубликованного (400).
- Выражения и типы: `Hi {{ $trigger.name }}` → `Hi Аня`, `0` и `false` сохраняются.
- Секреты во входе маскируются в результатах шагов (`[REDACTED]`).
- Вебхук: неверная подпись → 401, повтор с тем же `x-idempotency-key` дедуплицируется.
- VIEWER: читает, но не может править, публиковать, запускать, создавать учётные данные, отменять (403).

## Найденные проблемы

| # | Важность | Проблема | Как воспроизвести |
|---|---|---|---|
| S-1 | **Критично** | **После перезапуска API всё теряется, а `/setup` снова открыт: любой, кто достучится до порта, становится OWNER.** Пользователи, сессии, сценарии, учётные данные и история живут только в памяти. В compose порт API `4000` опубликован наружу. | `run` → перезапуск → `after-restart`: `bootstrapped:false`, вход 401, повторный setup 201 |
| S-2 | **Критично** | **Шаги-коннекторы «успешно выполняются», ничего не делая (BUG-01 в бэкенде).** Ни API, ни worker не регистрируют исполнители коннекторов (`registerExecutor` нигде не вызывается), и движок для неизвестного типа узла возвращает его конфиг как результат со статусом SUCCEEDED. | `core.telegramBot` с `chatId: 1` без учётных данных → `SUCCEEDED`, вывод = конфиг, сетевого запроса нет |
| S-3 | **Критично** | **Worker не связан с API.** API выполняет сценарии сам и ничего не ставит в очередь; worker работает только с Postgres + BullMQ. Миграции БД никто не запускает (`db:migrate` есть только как скрипт через `tsx`, в compose шага нет), поэтому в Docker worker, судя по коду, будет падать в цикле на `relation "executions" does not exist`. | `node apps/worker/dist/index.js` без БД падает на первом SQL-запросе; в API 0 упоминаний очереди |
| S-4 | **Критично** | **Веб-контейнер не может стартовать.** `infra/Dockerfile.web` запускает `apps/web/dist/server.js`, а такого файла нет: `apps/web` — библиотека контроллеров без сервера и экранов. С `restart: unless-stopped` это вечный перезапуск. | `pnpm --filter @localflow/web build` → в `dist/` нет `server.js` |
| S-5 | Высокая | **Чужой пользователь читает события любого запуска.** `GET /executions/:id/events` не проверяет права (в отличие от `GET /executions/:id`), отдаёт результаты шагов. | Пользователь вне пространства → 200 и поток событий; `GET /executions/:id` → 403 |
| S-6 | Высокая | **`PUT /draft` с телом не в JSON отвечает 200 и стирает черновик** (`nodes: []`). | `PUT /workflows/:id/draft` с телом `not json` |
| S-7 | Высокая | **`/health/ready` всегда отвечает `database: healthy, redis: healthy`**, хотя API к ним не подключается. Healthcheck не ловит реальные отказы. | `GET /health/ready` |
| S-8 | Средняя | Подпись вебхука сверяется с пересобранным JSON, а не с исходными байтами: настоящие отправители (GitHub, Stripe) подписывают тело как есть, поэтому `{"a": 1}` с пробелом и верной подписью → 401. | см. скрипт, шаг 9 |
| S-9 | Средняя | BUG-04 исправлен только в `apps/web`: API по-прежнему строит slug через `[^a-z0-9]`, «Моя команда» → `primary`, и slug не возвращается в ответе `/setup`. | ответ `/setup` без `slug` |
| S-10 | Средняя | Ошибки ввода при настройке отдаются как 500 `ERR_INTERNAL` (`Valid email address is required.`), а не 400/422 с кодом поля. | `/setup` с `email: "bad"` |
| S-11 | Средняя | Отмена завершённого запуска перезаписывает статус `SUCCEEDED` → `CANCELLED`, история искажается. | `POST /executions/:id/cancel` после успешного запуска |
| S-12 | Средняя | `credentialId` в узле должен быть UUID (`z.string().uuid()`), а API выдаёт id вида `cred_9f7d47cd` — привязать сохранённые учётные данные к шагу нельзя. | схема `WorkflowNodeDataSchema` |
| S-13 | Низкая | Учётные данные без `name` и `type` принимаются (201). | `POST /credentials` с `{}` |
| S-14 | Низкая | Нет эндпоинтов, без которых UI не собрать: `GET /workflows/:id`, история запусков сценария, приглашение пользователей и ролей, проверка подключения, удаление. | 404 `ERR_ROUTE_NOT_FOUND` |

**Про существующий E2E-набор** (`tests/run-e2e.mjs`, 286 зелёных тестов в `TEST_READY.md`): он работает на симуляторах в памяти и не проверяет ни перезапуск, ни связку API ↔ коннекторы, поэтому S-1…S-4 он пропускает.

## Что не проверено

- Сам `docker compose up` (нет Docker): сборка образов, healthcheck'и, тома. S-3 и S-4 выведены из кода и локальной сборки.
- Worker с настоящими Postgres и Redis: восстановление после сбоя, задержки, очередь.
- Одновременное редактирование: в API нет ни версий черновика, ни детекта конфликтов — сохраняет последний.
- 429, таймауты и отключённый worker — их негде вызвать, пока коннекторы не подключены (S-2).

## Что чинить и в каком порядке

1. **Хранение в Postgres** для пользователей, сессий, пространств, сценариев, учётных данных и запусков (S-1) + запуск миграций при старте (S-3). Без этого любой перезапуск — потеря данных и захват сервера.
2. **Подключить коннекторы к движку** и падать с понятной ошибкой на неизвестном типе узла вместо pass-through (S-2).
3. **Решить, кто исполняет:** либо API ставит запуски в BullMQ и их берёт worker, либо worker пока убрать из compose (S-3).
4. Закрыть S-5 и S-6, сделать честный `/health/ready` (S-7).
5. Веб-сервер в `apps/web` (S-4) — это и есть следующий этап «настоящее веб-приложение».
